# PROPOSAL — Architectural Audit of `docs/` (AETHER v3.0.0)

**Scope**: `docs/` tree only (root core, `concepts/`, `agile/`, `decisions/`). `_archive/` and `src/sagiha/` excluded per mandate.
**Method**: Every claim below is re-derivable from the audited files by path and section. Where a quantitative claim is made about the measurement protocol, it was verified by simulation (script in Deliverable 2, Appendix A).
**Audit date**: 2026-08-06.

---

## Executive Summary

**Verdict: conceptually the strongest documentation set this project has produced; operationally not yet safe to lock.** The doctrine — instruments before capability, gates over calendars, lift over absolutes, reversal conditions on every decision, mechanical enforcement over discipline — is coherent, internally cited, and superior to what most production agent teams write down. The Phase 0 audit register (`concepts/rewrite_v300_phase0_audit_register.md`) is genuinely exceptional epistemic hygiene.

However, the tree currently **fails its own standards in at least seven mechanically checkable ways**, and two of those failures sit exactly in the defect classes the documents were written to prevent:

1. **The statistical admission protocol is underpowered against its own committed target.** At N = 50, exact McNemar has 12–32% power to detect a true +10-point lift (simulation, Deliverable 2 §3). ADR-0003 as written will systematically *reject genuine improvements* — the inverse of the false-positive failure it was designed against, and just as expensive.
2. **The A/A floor is sequenced before B4**, so the floor's denominator can legally contain exit-127 instrument errors — a direct violation of `measurement.md` §2's "an instrument failure is never a data point," inside the document that states the rule.
3. **Sprint-01 violates ADR-0005 on its face**: Task 2 lands all nine port protocols; the backlog contains exactly one adapter (TASK-011). "A port enters in the same change as its first adapter and its conformance test. No exceptions" — no exemption is invoked, no second adapters named.
4. **The TCB_PATHS migration trap that ADR-0006 names as its own kill-switch has no owning task.** Sprint-01 creates the first `src/aether/` files; nothing in the sprint or backlog moves `.importlinter` / `TCB_PATHS` in that same change. If Sprint-01 ships as written, the ADR-0006 guarantee "evaporates while CI stays green" — the ADR's own words.
5. **Every core document links to a directory that does not exist** (`docs/00/`; the directory is `docs/concepts/`), while `STATUS.md` reports the relative-link gate green. Either the gate does not check these files or the claim is unsupported — both are the "gate that cannot fail" defect class.
6. **The repair loop — named in `vision.md` §2 as "the single largest lever on score in the system" — appears in zero milestones, zero backlog tasks, zero ADRs, and is absent from the M1a pipeline** (`retrieve → generate → apply → evaluate` has no repair edge). The project's stated biggest lever is unplanned. Compaction, named in the same paragraph, is equally absent.
7. **The normative word budget has silently inflated 3.6×** (Sprint-01 DoD: `--max 54000`; the Phase 0 record and audit register: ceiling 15,000, actual 13,941) with no ADR, no changelog, no mention anywhere.

None of these is fatal; all are fixable in one documentation sprint plus two small ADRs. But locking the tree with them in place would reproduce the predecessor's signature failure: rules stated and not enforced.

## Deep-Dive Critique

### 1. Vision & mission integrity

The lift-vs-absolute framing is the best strategic decision in the tree: it is the only metric that survives model swaps, and both Phase 0 tracks independently converged on it (the strongest available evidence it is real). Two vision-level gaps:

**The lift baseline is under-specified.** "A bare model call" admits a family of baselines: single-shot patch generation? Bare model with tool access but no harness? With how many tokens? The lift number is exquisitely sensitive to how weak the baseline is — a hostile reviewer will say the +10 was manufactured by choosing a straw baseline. Pin it in `measurement.md`: e.g. "single completion, task text + gold-file localization hint absent, official SWE-bench inference template, one attempt, no execution feedback," with the template hash recorded. The baseline is part of the instrument.

**The competitive claim has no instrument.** The mission is to outperform Grok Build, OpenHands, and Claude Code, but nothing in `docs/` defines how that comparison is ever measured on your own instruments — and `spec.md` §9 explicitly forbids using their published numbers as evidence. As written, the tree can *never* substantiate its own mission statement. The fix is a harness-comparison rig (Deliverable 2 §4): run OpenHands (open-source, directly runnable) and, where licensing permits, Claude Code, on the identical pinned task manifest with the identical model, through your evaluator. That yields *comparative lift* — the only apples-to-apples number that exists in this space — and it is a publishable artifact competitors mostly cannot produce.

### 2. System boundaries & decoupling

The hexagonal core, I1–I10, the single choke point, and wire-serializable ports (I3) are the right skeleton, and I3 in particular is correctly identified as the invariant that makes everything else cheap to reverse. Three boundary defects:

**The TCB has a residency ambiguity (D8).** The tree's most important boundary — Generator ≠ Evaluator — is enforced by path-keyed import contracts, so *where the Evaluator's concrete class lives* is not a style question; it decides whether the contract selects it. Resolve by rule, not convention.

**Half the packages float outside the layer lattice (D9).** `workflow/` is arguably the most architecturally novel package in the system (no reference implementation exists, per ADR-0013) and it has no declared position in the import order. `evolution/` is constrained by one named contract (`tcb-isolation` forbidden-importer) but its full import surface is undefined — can it import `agency/`? It is offline, but "offline" is not an import rule. Publish the full lattice.

**Ports are wire-serializable but not versioned.** For a project whose thesis is "swap anything," there is no port versioning/compatibility rule anywhere in the live tree (the archive had one; it was not carried forward). A one-paragraph rule suffices at this stage — e.g. "port protocols are frozen per minor version; additive-only changes within a minor; a breaking change is a new protocol name" — but its absence will be felt the first time a growth-tier port lands.

### 3. ADR integrity

The reversal-condition discipline is excellent and rare. The set nonetheless contains one internal contradiction (D11: ADR-0003 cost-flat vs ADR-0007 cost-delta), one gated invariant over an undefined structure (D10: the five layers), one status inconsistency (D17), and — most importantly — one decision whose enforcement is unowned (D4). ADR-0006 is unusually self-aware: it names the exact mechanism by which its own guarantee dies. That the plan then fails to assign that mechanism an owner is the single most ironic defect in the tree, and the cheapest S1 to fix.

A missing ADR: **repair-loop design** (D7). ADR-0013 fixed the pipeline as `retrieve → generate → apply → evaluate` — a DAG, hence acyclic, hence structurally incapable of expressing the repair *cycle* the vision calls the biggest lever. Either the workflow abstraction supports bounded cycles (iteration nodes with a budget), or repair lives inside the `generate` node as loop logic invisible to memoization and ablation — which forfeits exactly the per-node ablation machinery M2 exists to buy. This is a real design fork and deserves ADR-0014/0015 treatment before M1a, not after.

### 4. Decoupling for the stated end-state

Measured against the stated goal — "small decoupled blocks, easily swappable, harness engineering and loop engineering as first-class activities" — the current seams are *almost* sufficient. What is missing is that **the workflow topology itself is code, not data**. If loop engineering means routinely trying `retrieve → plan → generate → evaluate → repairⁿ` against `retrieve → generate×N → rank → evaluate`, then each variant being a code change means each variant is a PR, a review, and a redeploy — which throttles the experiment cadence that the whole memoization/ablation apparatus exists to accelerate. The fix (declarative workflow definitions as versioned data, admitted through the ADR-0003 gate) is the load-bearing proposal of Deliverable 3, because it is simultaneously the enabler for human loop-engineering now and machine self-redesign later, under the same TCB rules.
